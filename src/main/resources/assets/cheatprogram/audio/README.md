# Selected-application audio capture

`process-audio.exe` is an original C# COM interop implementation of Microsoft's documented application-loopback API. Rebuild locally with `process-audio.ps1 -CompileOnly`; only the Windows .NET Framework C# compiler is required. It does not install a driver, alter default playback devices, capture a microphone, or record audio files.

## Scope and platform

Requires Windows build 20348 or newer and an application that supports shared-mode process loopback. The explicit selected process **and its child processes** are included. Audio belongs to an application process tree, not a specific browser tab; windows sharing a browser process may share audio. The helper rejects Minecraft itself and an ancestor process tree containing Minecraft. There is no system-wide loopback fallback, so spatial playback cannot feed recursively into its capture. DRM-protected or exclusive-mode audio may not be capturable.

`AppAudioCapture.start(pid, muteOriginal, Consumer<Pcm>)` delivers newly owned PCM16 little-endian packets, 48 kHz, two channels, on an IO thread. Consumers must enqueue them without blocking. `stop()` is nonblocking, including pipe shutdown. Subsequent starts wait for earlier helpers to exit, off the game thread. The helper retains source/owner process identities until capture ends, so PID reuse cannot transfer capture to another process. It checks their lifetimes and a one-second Java heartbeat; stdin EOF, `Q`, or an eight-second lease expiry stops it. Java extracts the binary by content hash to avoid overwriting a helper still used by another game instance. Zero PCM reports silence instead of a misleading live-audio status. No audio is saved to disk.

## Original-audio suppression: explicit limitation

On this machine, a controlled synthetic 440 Hz source measured RMS 207 before session mute, 0.48 after mute, and 210 after restoring the original mute state. Muting the application also removes useful audio from its process-loopback capture. Querying `IAudioClient2` on this virtual capture client returns `E_NOINTERFACE`; the documented `POST_VOLUME_LOOPBACK` stream option cannot provide an application-session pre-mute route here.

The low-level `process-audio.exe` still rejects its suppression flag with status 103 **without capturing or changing any session volume/mute bit**. Muting the browser tab itself generally removes the source audio and is not a substitute. The spatial-audio manager instead uses the separate, reversible endpoint-routing helper below: it starts unmuted process capture only after all currently active source audio sessions are verified on the unmonitored virtual output. Minecraft continues to play through the listening device. An explicit setup action in the UI manages the optional external driver; neither of these native helpers installs a driver.

The production helper never changes system/session volume. No restoration operation is necessary on normal exit or crash. An isolated diagnostic implementation with a restoration guard was used only for the owned-source experiment; it is not shipped or used by the mod.

## Selected-application output routing

`audio-route.exe` is a separate original COM-interop helper; rebuild with `audio-route.ps1 -CompileOnly`. It uses the per-application audio-policy ABI described by EarTrumpet's MIT-licensed interoperability declarations. `check` reports active CABLE input/output availability, policy support and whether Windows playback defaults are safe. `route <sourcePid> <ownerPid> <journal>` routes only the selected application's process tree and all three of its render roles. It does not route the system-wide mix, change session mute/volume, or change the Windows default playback device. A separate, explicit `restore-defaults <snapshot>` command exists for the driver's installation workflow; it is never called by an active route lease.

The original application endpoint choices and process start identities are written atomically before any route is changed. The route helper and its independent watchdog both acquire process handles before a new identity can be routed, protecting against PID reuse. Only processes with active render sessions receive route writes: a browser's silent parent/utility processes can reject endpoint writes with `E_INVALIDARG` even while a child is playing. Newly active descendants are discovered on the next inspection. A new process of an already recorded executable reuses that executable's saved original choices, rather than mistaking CABLE for the original output. Subsequent user changes are respected, including when another audio child starts later: an application moved away from CABLE is not forced back, and cleanup restores only roles still pointing to the helper's CABLE endpoint. Inactive helper/console processes with no audio policy identity are not counted as failed live audio sessions.

`ready=true` requires at least one active selected audio session, **every** active selected render session to be located on CABLE, and all active audio identities' persisted render roles to point to CABLE. Merely writing an application policy does not establish readiness. Existing WinMM, exclusive-mode or non-migrating application streams may remain on their previous endpoint; status stays `waitingApp` and spatial replay is withheld until the source opens a stream on CABLE. Such applications may require restarting their own audio playback/application. Audio from browser windows sharing the same process is still process scoped.

The route lease inspects sessions every 350 ms and reports unchanged status at least every two seconds. Java treats a ready report older than four seconds as unverified and withholds replay. Process-tree enumeration uses a native Toolhelp snapshot, avoiding repeated WMI queries. Journals are rewritten and synchronized with the watchdog only when identities or applied routes change. Completed restoration journals are skipped during reconnect recovery; accumulating history no longer starts one native restore process per past lease.

The owner sends `P` heartbeats. `Q`, stdin EOF, source/owner exit, or eight seconds without a heartbeat ends the lease and attempts restoration. If the route helper is terminated, its watchdog restores the journal under the same per-user mutex; explicit journal recovery also acquires that mutex and refuses a live route lease. Possible partial writes are journaled before changing the first role, and untouched utility executables do not create false restoration failures. Restoration prefers active audio identities over silent parent processes. On this Windows build, an already exited application can reject per-app policy calls **even while its process handle is retained**. That outcome is saved as `restorePending` with `restored=false`; it is never reported as restored. The next live instance of the same executable must first recover that journal before taking a new original-route snapshot. The mod does not automatically launch an arbitrary application to force recovery.

Owned-fixture verification used a WASAPI source that opened CABLE explicitly, with a silent bootstrap session and a very low-level 220 Hz signal only after its application policy selected CABLE. It never opened a physical/default output. Verified cases include normal `Q` restoration, route-helper termination followed by watchdog restoration, eight-second heartbeat expiry, later user route changes, and source exit with truthful pending state followed by restoration on the owned application's restart. Process-loopback PCM remained nonzero while the real selected session was on CABLE. These tests do not establish compatibility with every browser, media player, DRM stream or game audio configuration.

## Binary protocol

Every record has a 40-byte little-endian header: eight signed 32-bit values (`0x31415043`, status, 48000, 2, frame count, payload bytes, HRESULT, original-muted flag), then a signed 64-bit sequence. Status `1` carries PCM payload (`frames*4` bytes, max 192000); all other records have an empty payload. `2` = ready; `3` = waiting/no audio; `4` = stopped; `101` = unsupported OS; `102` = activation/capture failure; `103` = original-audio suppression unavailable; `104` = invalid/unsafe source. Java validates magic, format, lengths and bounds before handing a packet to playback. Standard error contains only bounded API stage/HRESULT diagnostics, never source titles or audio.
