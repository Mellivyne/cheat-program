# Window capture and explicit application input

`window-capture.exe` is rebuilt locally by `window-capture.ps1 -CompileOnly` using the Windows .NET Framework compiler and the Windows WinRT metadata. No external runtime or package download is needed. Capture dimensions, native frame scheduling, and WGC restart behavior are independent of input.

## Live desktop sources

Desktop entries represent individual monitors, captured through WGC `IGraphicsCaptureItemInterop.CreateForMonitor`. The compositor supplies live application changes, window openings, and window movement on that monitor. `Progman` and `WorkerW` wallpaper hosts are excluded and rejected as window sources. Desktop capture naturally includes Minecraft when it is visible on the selected monitor.

A source has an explicit `window` or `monitor` kind. Monitor rows carry an exact `HMONITOR`, PID `0`, and an opaque identity combining the display-device name with its per-monitor interface path from `EnumDisplayDevices(EDD_GET_DEVICE_INTERFACE_NAME)`. Every capture state check validates both the handle and identity; a missing monitor closes that source instead of selecting another monitor. A monitor without a verifiable interface identity is not offered. Monitor frames use their full native dimensions without applying a window client-area crop. Native size and source-driven frame scheduling keep the existing meaning. Selecting GDI for a desktop still uses WGC, and WGC failures reconnect without a static screenshot fallback.

Desktop capture is view-only: background input and foreground-window activation require an application window. A monitor does not identify an audio process; selected-process audio and subtitle speech capture must not treat PID `0` as whole-system audio.

The native listing protocol has seven tab-separated columns: handle, PID, Base64 process/device label, Base64 title, minimized flag, source kind, and Base64 source identity. Window capture accepts its legacy ten arguments, twelve arguments with source kind/Base64 identity, or fourteen arguments also retaining the original root HWND/PID across active-view reconnects. Java retains the five-argument `Window` constructor for application sources and uses `sourceKey()` for exact live source identity. Monitor persistence stores the kind and opaque identity so refresh can rebind only the same monitor and display-device pairing. The helper is extracted by binary content hash, avoiding collisions with another game instance's still-running helper.

Reference: https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createformonitor

## Background scrolling

Chromium/CEF input explicitly finds its known `Chrome_RenderWidgetHostHWND` receiver even when it carries `WS_EX_TRANSPARENT`, instead of choosing a presentation-only D3D child or its parent. The search remains bounded within the selected app and validates visibility, enabled state and point bounds. These sources receive their actual wheel messages before any accessibility fallback, preserving horizontal/vertical fractional deltas and modifiers. Held-button drags preserve ordered samples and the final move before release; ordinary hover remains coalesced.

Quiet WGC frame pools recover in place with increasing 2/8/30/60-second delays. Repeated unchanged initial frames do not reset that backoff. The last complete Java texture stays visible, and the helper retains the original size/cadence rather than switching to a static GDI fallback. This addresses a gap where status heartbeats prevented the old watchdog from noticing a stopped frame stream; it does not imply that every application continues its own playback while backgrounded.

The selected window is the sole root for a bounded accessibility-tree search. A private `CUIAutomation8` client sets and verifies `IUIAutomation2.AutoSetFocus = FALSE` before obtaining elements or patterns. This is essential: the older managed `ScrollPattern` wrapper automatically focuses a target before executing an action. The helper uses `IUIAutomationScrollPattern.SetScrollPercent` only; it never invokes `SetFocus`, `ScrollIntoView`, a click, or a foreground fallback. Fractional wheel input changes fractional offsets instead of being discarded until a full notch accumulates.

Standard Win32 Edit, RichEdit, ListView, ListBox and TreeView controls receive immediate bounded native wheel messages at the validated child instead of waiting for an accessibility search. Framework/custom controls retain the focus-disabled accessibility path and native fallback. The search has a 150 ms budget; incomplete or truncated searches remain retryable rather than being cached as permanent unsupported results. Wheel fractions and both axes remain supported where the target control accepts them.

The helper also verifies Minecraft is still foreground before each queued input request and each asynchronous scroll step. Leaving explicit interaction clears pending requests and releases posted buttons/keys. Mouse movement is coalesced independently, with an event-driven writer wakeup and button boundary positions retained for drags. Repeated native moves at exactly the same client pixel/target/button state are suppressed. Input geometry reads cached metadata instead of uploading textures in mouse callbacks. Status-only acknowledgements are coalesced between complete video records, so a full video pipe cannot block delivery of the next input edge. No source-window styles or persistent application settings are changed.

Scroll patterns are retained for up to 750 ms at the same pointer location and invalidated at input/page boundaries. Consecutive same-direction wheel requests are combined before applying the offset; direction changes remain separate. A burst therefore does not perform an accessibility-tree walk for every wheel report. Chromium/CEF child windows are detected inside native host applications as well as at their top level.

## Input compatibility

Background interaction posts pointer/key messages to the selected window and its owned child windows. Ordinary controls can receive hover, clicks and drags, but applications that require OS raw input or a real foreground cursor may reject these events; background messages are not claimed to be hardware input. Page scrolling does not synthesize a browser `wheel` event, so custom canvas wheel actions can remain unsupported.

Input accepts legitimate child windows in other renderer processes while still excluding Minecraft and the helper itself. Background view focus notifications and the selected thread's focused child route committed text to the input control. Mouse drags keep the initial target through release, and a second click can be delivered as a double-click. Pointer/key message delivery does not call `SetForegroundWindow`, `SetFocus` or `AttachThreadInput`.

Text mode and keyboard-only mode both forward committed Unicode characters. Tapping left Ctrl switches movement/text mode; holding it for a shortcut no longer switches modes. Ctrl+V forwards up to 8192 characters of explicitly pasted text as UTF-8, without replacing the system clipboard. Full OS IME composition and software that requires hardware cursor events still require the separately selected system input mode.

The selector includes app-owned untitled popup windows and offers a same-application view filter with periodic refresh. Choosing a different view preserves the in-world screen placement and size; separate top-level windows remain separate capture sources. Content drawn into an application window changes naturally as that application's own UI navigates.

## New application views opened from a projection

Sibling views created on a different UI thread in the original process are supported. A show/focus event correlated with projected input can also return to an existing page. Releasing the interaction key releases all held input immediately while retaining the bounded five-second page-follow intent, so asynchronous loading does not cancel its own capture transition. Selecting another projection or stopping capture cancels it explicitly. Source create events protect relevant top-level windows before their final dimensions exist; menus, tooltips and IME surfaces remain excluded. The helper and protocol retain their original native dimensions and frame scheduling.

A projected button-down or activation key snapshots the currently visible top-level windows before forwarding input and arms a five-second follow interval. Only a newly visible relevant owned window or window in the selected application's process tree can replace that projection's active view. The intent ends after its first adopted view; selecting another projection sends the `F` control command to cancel an old unconsumed intent. Existing unrelated windows, other independently projected views, desktop sources, tiny tooltips and native popup menus are excluded. Merely hovering, scrolling, changing the foreground app, or creating an unrelated window without projected input does not select a new source. Closing/hiding a followed view returns to the last live original/parent view. WGC recreates its item on a view transition while Java retains the last texture, world placement, size and original audio source PID. Original-process lifetime identity is checked before audio can use that PID.

The native 52-byte record header remains unchanged. Status `20` is an active-view identity notification: header `number` is the new HWND and its bounded UTF-8 payload contains PID, Base64 process, Base64 title and a recovery-game HWND (or zero), separated by tabs. Java validates the record, clears stale input, and withholds new coordinate events until a complete frame of that view has reached the texture. A reconnect launches the current active HWND while retaining the original root for close fallback.

For a newly opened view correlated with projected input, the helper can place that new window behind the game using `SetWindowPos` with `SWP_NOACTIVATE`. If that exact new view activated itself, Java performs at most one recovery attempt to the game HWND verified at the original projected input. Recovery requires the exact new view to remain foreground and the game HWND to belong to the current JVM. A different foreground app invalidates the attempt, preserving user Alt+Tab. This does not guarantee every application's own activation behavior can be suppressed. The separately selected system-input mode continues to activate the current app view intentionally.

The optional `System mouse (switch to source app)` mode is selected separately and defaults off. Pressing the interaction key in that mode explicitly activates the chosen source window. The user then operates its normal system mouse/keyboard and uses Alt+Tab to return. No global `SendInput`, remote debugging port or input injection driver is installed or enabled by the default background mode.
